Manual de modelos
Copilot Becario

Guía de descarga, inputs, predicción, intervención y replanificación adaptativa. El paquete actual está entrenado con ScholarSim sintético y está listo para integrarse en una API o prototipo.

1. Paquete descargable

Descarga estos archivos juntos, manteniendo la estructura de carpetas:

  • manifest.json: semanas, barreras, umbral y metadatos.
  • week00.joblib: solo cuestionario inicial.
  • week03.joblib: corte de semana 3.
  • week06.joblib: corte de semana 6.
  • week09.joblib: corte de semana 9.
  • engine/models.py: cargador, predicción y entrenamiento.
  • engine/schedule.py: planificador greedy y CP-SAT.
Compatibilidad: los .joblib se cargan con el entorno del proyecto (uv run) y sus dependencias declaradas en pyproject.toml. Son modelos sintéticos; al pasar a producción hay que reentrenar con etiquetas validadas.

3. Inputs mínimos que debe capturar la aplicación

Iniciales

ID, carrera/cursos, diagnóstico, notas previas, temas difíciles, disponibilidad, trabajo, cuidados, conexión/dispositivo, apoyo y disposición a pedir ayuda.

Check-in semanal

Avance por curso, asistencia, horas disponibles reales, horas trabajadas/cuidados, conexión, carga percibida, bloqueo y motivo declarado.

Planificación

Horarios de clase, trabajo, cuidados, traslados, exámenes, horas objetivo, competencias a reforzar, sesiones fijadas y preferencias.

Contexto de apoyo

Campus/sede, tutor disponible, servicios, modalidad, canal preferido, urgencia, consentimiento y fecha de última actualización.

Regla práctica: si un dato cambia el plan o la intervención, debe guardar valor, fecha, fuente y nivel de confianza.

4. Cinco macroperfiles de becarios

PerfilSeñalesIntervención principal
1 Trayectoria estableAvance sostenido, disponibilidad suficiente y ninguna barrera sobre el umbral.Seguimiento ligero y planificación.
2 Barreras académicasBrechas, cursos desaprobados, notas bajas o temas difíciles.Refuerzo por competencias y tutorías.
3 Barreras de tiempoTrabajo, cuidados, traslados, caída de horas disponibles o sobrecarga.Optimización del calendario y recuperación gradual.
4 Barreras materiales y digitalesConectividad, dispositivo, materiales, pago/recursos o acceso físico.Recursos offline, préstamo y derivación a apoyos.
5 Barreras de integración y motivaciónAdaptación difícil, poco apoyo, duda de continuar o baja disposición a pedir ayuda.Orientación, acompañamiento humano y comunidad.

Los modelos descargados estiman cuatro barreras y clasifican como estable cuando ninguna supera el umbral de 0,5. Por eso los cinco macroperfiles están cubiertos sin convertirlos en etiquetas excluyentes.

6. Replanificación ante externalidades

El plan semanal puede actualizarse sin rehacer todo desde cero. Registrar la externalidad, recalcular la capacidad y enviar el plan anterior al solver:

from engine.schedule import cpsat_plan, busy_blocks

busy = busy_blocks(profile, schedules, extra=blocked_blocks)
nuevo = cpsat_plan(
    week=semana_actual,
    targets=targets_actualizados,
    busy=busy,
    capacity_hours=horas_disponibles,
    previous=plan_anterior.sessions,
    pinned=sesiones_fijadas,
)
# nuevo.to_dict() entrega sesiones, faltantes y cantidad de cambios

El CP-SAT respeta sesiones fijadas, evita horarios ocupados, prioriza objetivos y minimiza cambios del plan anterior. Si no alcanza la capacidad, conserva shortfall para decidir una recuperación.

Semana perdida: recuperación moderada

Si se pierde la semana 3, la próxima semana se suma una fracción del faltante, no todo de golpe: horas_recuperación = min(25% del faltante, 1 hora), siempre respetando el máximo diario de 4 horas y las restricciones del becario. La prioridad se reparte entre cursos y el resto queda como pendiente visible.

7. Comandos de referencia

uv run python -m engine.models train
uv run python -m engine.models predict b-00004 --week 6
uv run pytest -q

Para una API, envolver predict en un endpoint que reciba student_id y week; para replanificar, recibir disponibilidad, objetivos, externalidades y sesiones fijadas.

8. Límites y uso responsable

  • Los resultados actuales son de un simulador y pueden ser optimistas.
  • Una probabilidad no es un diagnóstico ni debe decidir sola una sanción, beca o retiro.
  • Los motivos declarados y la validación de tutores deben alimentar las etiquetas reales.
  • Guardar solo datos necesarios, con consentimiento, control de acceso y trazabilidad.
  • Revisar sesgos por carrera, sede, discapacidad, trabajo y conectividad antes de producción.

Simulación semanal

engine/simulation.py permite recorrer semanas sin NLP ni datasets: cada externalidad es una opción cerrada. En cada semana devuelve macroperfiles activos, horas disponibles y perdidas, recuperación, riesgo, alerta, intervención, perfiles de apoyo y acción del planificador.

from engine.simulation import simulate; recorrido = simulate({3: "laptop_dañada", 6: "trabajo_extra"}, weeks=9)

Una laptop dañada activa la barrera material/digital, crea una alerta, recomienda soporte TI y biblioteca, reduce horas disponibles y deja una recuperación gradual para la semana siguiente. Si luego aparece trabajo extra, se agrega la barrera de tiempo sin borrar la anterior.
